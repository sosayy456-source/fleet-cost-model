### ข. เว็บค้างและล่ม (ฝั่งเบราว์เซอร์)

อาการ "หน้าไม่ตอบสนอง" = JavaScript ค้างนาน · "แย่จัง!" หลัง refresh = แท็บพัง ส่วนใหญ่หน่วยความจำไม่พอ
(ไม่ใช่ dev server ตาย — ถ้า server ตายจะขึ้น "localhost ปฏิเสธการเชื่อมต่อ")

1. **`costrev/trips.json` ก้อนใหญ่ โหลดทั้งก้อน** — ชุดตัวอย่าง 10,798 เที่ยว = 13.6 MB (~1.26 KB/เที่ยว)
   ข้อมูลจริงเที่ยวมากกว่าราว 10 เท่า → ราว 100+ MB และหน่วยความจำในแท็บหลายร้อย MB ถึง ~1 GB (**ประมาณ ยังไม่ได้วัดกับข้อมูลจริง**)
   - เก็บเป็นแถว: object 50 คีย์ต่อเที่ยว ชื่อคีย์ซ้ำทุกแถว
   - ช่อง `cus` (รหัสลูกค้า hash ยาว 64 ตัว) กิน **23%** ของไฟล์ · `vs` 9%
2. **ดึงทุกไฟล์ด้วย `cache: "no-store"`** (`lib/data/useCostRev.ts` · `useAlloc.ts` ฯลฯ) — refresh ก็ดาวน์โหลด+แปลงใหม่ทั้งก้อน
   ขณะที่แท็บเดิมยังคืนหน่วยความจำไม่หมด → "แย่จัง!"
3. **`old_records.json` โหลดตอนเปิดแอปทุกหน้า** (`useRecords` ระดับ App → `loadCostRevOld()`) ทั้งที่ใช้แค่หน้ารายการทั้งหมด/ลูกหนี้
4. **หน้า Executive Dashboard คิดทุกอย่างพร้อมกัน** — 4 ส่วน + Performance Index 5 หมวด + แผนที่ จากทุกเที่ยว
   เปลี่ยนตัวกรองหนึ่งครั้งคิดใหม่หมด (เช่น `vehicleRows()` ทุกคัน · `rollupCustomers` ทุกลูกค้า)
5. **นำเสนอผ่าน `npm run dev`** — React โหมดพัฒนาช้ากว่าตัว build หลายเท่า และเครื่องเดียวกันมีตัวเฝ้าไฟล์/python รันอยู่

## ทางแก้ (เรียงตามลำดับที่ควรทำ)

แต่ละข้อทำแยกกันได้ · หลังทุกข้อต้องตรวจว่า **ตัวเลขบนจอเท่าเดิม** (ดู "วิธีกันตัวเลขเพี้ยน" ท้ายไฟล์)

### 0. ก่อนนำเสนอ — ไม่ต้องแก้โค้ด
- แปลงไฟล์ให้เสร็จล่วงหน้า ห้ามแตะ `etl/data/` ระหว่างนำเสนอ
- นำเสนอจากตัว build: `cd app` → `npm run build` → `npx vite preview` (ไม่มีตัวเฝ้าไฟล์ React โหมดจริง)
  **ห้าม push ตอนมีไฟล์ใน `app/public/data/real/`** (workflow fail อยู่แล้ว)
- ใช้ Chrome/Edge แท็บเดียว ปิดโปรแกรมอื่น — ช่วยได้แต่ไม่รับประกัน เพราะไฟล์ยังใหญ่เท่าเดิม

### 1. ย่อ `trips.json` — แก้อาการล่มตรงที่สุด
- ETL (`build_costrev.py`): เปลี่ยน `cus` เป็นเลขลำดับ + ส่งตารางรหัสแยกไฟล์ (`cus_codes.json`) · เก็บเป็นคอลัมน์แทนแถว
  (แบบเดียวกับ `loadfactor/trips.json` ที่ทำเป็นคอลัมน์อยู่แล้ว)
- แอป (`useCostRev.ts`): แปลงกลับเป็น `Trip[]` ตอนโหลด ให้หน้าจอไม่ต้องแก้ · ถ้ายังหนัก ค่อยให้หน้าจออ่านคอลัมน์ตรง
- ที่ใช้ `cus`: กำไร/ลูกค้า ในหน้า Executive Dashboard (นับลูกค้าไม่ซ้ำเป็นเซ็ต — เลขลำดับนับได้เหมือนเดิม)
- คาดว่าไฟล์และหน่วยความจำลดเกินครึ่ง · ต้องรัน `build_costrev.py` ใหม่

### 2. ไม่คิดทั้งหน้าพร้อมกัน
- หน้า Executive Dashboard: วาด/คำนวณส่วนที่ 2–4 และกล่อง PI เมื่อเลื่อนใกล้ถึง (IntersectionObserver)
  **คะแนนรวม /100 ต้องได้ครบทุกหมวด** → กล่อง PI คิดคะแนนได้โดยไม่ต้องวาดเนื้อหาส่วนนั้น หรือคิดหลังหน้าแรกวาดเสร็จ
- โหลด `old_records.json` เฉพาะหน้ารายการทั้งหมด/ลูกหนี้/ใบที่ยังไม่ครบ (ย้ายออกจาก `useRecords` ระดับ App)

### 3. ให้เบราว์เซอร์ใช้แคช
- เลิก `cache: "no-store"` กับไฟล์ข้อมูลก้อนใหญ่ · ต่อ `?v=<generatedAt ของ manifest>` ท้าย URL
  (manifest ยังดึงแบบ no-store เพื่อรู้ว่ามีรุ่นใหม่) — ETL รันใหม่ = คีย์แคชใหม่ ไม่ได้ข้อมูลเก่าค้าง

### 4. ETL เร็วขึ้น — ไม่เกี่ยวกับอาการล่ม ทำทีหลังได้
- ตัดงาน `rev` (`build_json.py`) ออกจาก `autoEtl` · ป้าย "ข้อมูลตัวอย่าง" ของ App ให้ดูจาก `costrev/manifest.json` แทน
  (**ตรวจก่อนว่า** `lib/dataset.ts`/`useActiveDataset` ไม่มีที่อื่นพึ่ง `cube.json`/`dimensions.json`) → ประหยัด ~20–40 นาที
- ตัวเฝ้าไฟล์: สั่งงานเฉพาะเมื่อ รายชื่อ/ขนาด เปลี่ยน ไม่ดูเวลาแก้ไขอย่างเดียว · และไม่สั่งซ้ำถ้าลายเซ็นเท่ากับตอนเริ่มรอบที่กำลังรัน
- อ่านไฟล์รายได้รอบเดียว เก็บเฉพาะคอลัมน์ที่ต้องใช้ลงไฟล์กลาง (parquet ใน `etl/.cache/` — ห้ามอยู่ใต้ `public/` และต้องอยู่ใน `.gitignore`)
  แล้วให้ `build_costrev` / `build_alloc` อ่านจากไฟล์กลาง · ครบชุดน่าจะเหลือไม่กี่นาที · **ระวังหน่วยความจำ** — ยังต้องทำทีละไฟล์ตามกฎใน CLAUDE.md

## วิธีกันตัวเลขเพี้ยน (ทำทุกข้อ)

1. **ก่อนแก้**: รัน ETL ชุดตัวอย่าง (`build_costrev.py --dataset sample` · `build_alloc.py --dataset sample`) เก็บผลเดิมไว้เทียบ
   และจดตัวเลขหน้าจอสำคัญ: การ์ดกำไร/รายได้/ต้นทุน · คะแนน PI รายตัว + รวม /100 · Top 10 กำไรลูกค้า · % เที่ยวเปล่า
2. **หลังแก้**: ข้อ 1/4 — แปลงไฟล์ใหม่แล้วแอปต้องได้ `Trip[]` เท่าเดิมทุกฟิลด์ (เขียนเทสต์เทียบ JSON เดิมกับที่แปลงกลับ)
   ข้อ 2/3 — ตัวเลขหน้าจอเท่าเดิมทุกตัว · `npm test` ผ่าน
3. **กับข้อมูลจริง**: ทำชุดตัวอย่างผ่านก่อน แล้วค่อยรันข้อมูลจริง เทียบตัวเลขที่จดไว้ก่อนแก้
   วัด ขนาดไฟล์ · เวลาโหลด · หน่วยความจำแท็บ (Chrome Task Manager) ก่อน/หลัง
4. แก้ทีละข้อ commit ทีละข้อ — ตัวเลขเพี้ยนย้อนกลับได้ทันที
