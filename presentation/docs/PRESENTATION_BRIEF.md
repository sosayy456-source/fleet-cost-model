## 1. ทำไมต้องมีเว็บนี้

ตอนนำเสนอโมเดลจริง (25 ก.ย. 2569) แอปหลัก (`app/`) โหลดข้อมูลจริงแล้วค้าง ขึ้น "หน้าไม่ตอบสนอง"
และ refresh แล้วแท็บพัง ("แย่จัง!") สาเหตุคือแอปหลักโหลดไฟล์เที่ยวทั้งก้อน (ประมาณ 100+ MB) แล้วคำนวณทุกอย่างสดในเบราว์เซอร์
รายละเอียดอยู่ใน `docs/แผนแก้-ข้อมูลจริงช้า.md` ที่ root ของ repo (เจ้าของงานยังไม่ให้แก้แอปหลัก)

**ทางออกสำหรับการนำเสนอ:** แยกเว็บเล่าเรื่องออกมาต่างหาก ใช้ **ตัวเลขสรุปที่คำนวณไว้แล้ว** (ไฟล์ JSON เล็ก ๆ ไม่กี่ KB)
ไม่โหลดข้อมูลดิบ ไม่คำนวณหนักในเบราว์เซอร์ เล่าเป็นฉาก (scene) เลื่อนลงอย่างเดียว มีแอนิเมชันลื่นเหมือนวิดีโอพรีเซนต์

## 2. เว็บนี้คืออะไร / ไม่ใช่อะไร

| เป็น | ไม่เป็น |
|---|---|
| เว็บเล่าเรื่องแบบ scroll ลงอย่างเดียว แบ่งเป็นฉาก | แดชบอร์ดที่กรอง/เจาะข้อมูลได้ |
| แอนิเมชันผูกกับการเลื่อน (scrub) และเข้าฉากนุ่ม ๆ | ตัวแทนของแอปหลัก — แอปหลักยังใช้งานตามเดิม |
| ตัวเลขสรุปคงที่จากไฟล์ `story.json` | ที่คำนวณสูตรใหม่ — สูตรมีที่เดียวคือ `app/src/lib/` |
| เปิดได้แบบออฟไลน์ (ไม่พึ่งเน็ตที่ห้องสัมมนา) | เว็บที่ต้องต่อ Google Sheet / Apps Script |

## 3. ผู้ชมและบริบท (สมมติฐาน — ให้เจ้าของงานยืนยัน ดูข้อ 9)

- ผู้ชม: อาจารย์/กรรมการสัมมนา และผู้บริหารบริษัทขนส่ง (เจ้าของข้อมูล) — รู้ธุรกิจขนส่ง ไม่จำเป็นต้องรู้เทคนิค
- ความยาว: ราว **15–20 นาที** ผู้นำเสนอเลื่อน/กดปุ่มเองทีละฉาก พูดประกอบ
- จอ: โปรเจกเตอร์ 1920×1080 หรือ 1280×720 · สำรองด้วยโน้ตบุ๊ก 1366×768
- ภาษา: ไทยเป็นหลัก ชื่อส่วนเป็นอังกฤษตามแอปหลัก (Executive Dashboard · Profit Per Route ฯลฯ)

## 4. สารหลักที่ผู้ชมต้องจำได้ (key messages)

1. บริษัทไม่รู้ **ต้นทุนจริงต่อเที่ยว ต่อเส้นทาง ต่อลูกค้า** เพราะข้อมูลกระจายอยู่ใน Excel หลายสิบไฟล์
2. โมเดลนี้ **รวมข้อมูลรายได้กับต้นทุนเข้าด้วยกันรายเที่ยว** และแยกต้นทุนเป็น คงที่ · ผันแปร · กึ่งผันแปร · สูญเปล่า
3. เห็น **เงินที่รั่วไหล** ชัด ๆ: รถวิ่งไม่เต็มคัน (Load Factor) · เที่ยววิ่งเปล่า · เส้นทาง/ลูกค้าที่ขาดทุน
4. มี **Performance Index 100 คะแนน** สรุปสุขภาพการเดินรถ 5 ด้านในตัวเลขเดียว
5. มี **ระบบงาน 3 ฝ่าย** (บิล → จัดรถ → บัญชี) ที่เก็บข้อมูลใหม่ต่อเนื่อง ไม่ใช่รายงานครั้งเดียว

## 5. ข้อบังคับ (ห้ามพลาด)

1. **ห้ามแก้ระบบเดิม** — ห้ามแก้ไฟล์นอก `presentation/` ทั้ง `app/` `etl/` `map/` `apps-script/` `.github/` และ `.gitignore` ที่ root
   (อ่านได้ import ได้ แต่ห้ามเขียน) · ถ้าต้องกันไฟล์ให้ใช้ `presentation/.gitignore`
2. **repo เป็น public** — ห้าม commit ตัวเลขจากข้อมูลจริง ชื่อลูกค้าจริง ทะเบียนรถจริง
   ตัวเลขจริงอยู่ใน `presentation/src/data/story.real.json` ที่ gitignore ไว้เท่านั้น (ดู `IMPLEMENTATION_PLAN.md` ข้อ 5)
3. **ห้ามเขียนสูตรใหม่** — ตัวเลขทุกตัวต้องมาจากไฟล์ที่แอปหลัก/ETL สร้างแล้ว หรือเรียกฟังก์ชันใน `app/src/lib/` แบบอ่านอย่างเดียว
   (กฎของโปรเจกต์: "`lib/` = ตรรกะ · `features/` = หน้าจอ · ฟีเจอร์ห้ามมีสูตรของตัวเอง")
4. **ไม่พึ่งเน็ตตอนนำเสนอ** — ฟอนต์ รูป แผนที่ อยู่ในโฟลเดอร์ทั้งหมด ไม่โหลดจาก CDN
5. คอมเมนต์ เอกสาร และข้อความ commit **เป็นภาษาไทย** ตามโปรเจกต์
6. ไม่กระทบ workflow deploy ของแอปหลัก (`.github/workflows/deploy.yml` build เฉพาะ `app/`)

## 7. เกณฑ์ว่าเสร็จ (success criteria)

- เลื่อนจากต้นจนจบได้ลื่น **60 fps** บนโน้ตบุ๊กทั่วไป ไม่มีจังหวะกระตุกตอนเข้าฉาก
- โหลดครั้งแรก **< 3 วินาที** บนเครื่องเดียวกับที่ใช้นำเสนอ · ทั้งเว็บหลัง build **< 6 MB** (รูปรวม < 2.5 MB) · JS **< 300 KB gzip**
- เปิดได้โดย **ไม่ต่อเน็ต** (ทดสอบด้วยการปิด Wi-Fi)
- ผู้นำเสนอคุมได้ด้วยคีย์บอร์ด/รีโมตพรีเซนเตอร์ (→ ↓ Space PageDown = ฉากถัดไป · ← ↑ PageUp = ย้อน)
- ไม่มีตัวเลขจริงใน git (`git grep` ตัวเลขหลักจาก `story.real.json` แล้วต้องไม่เจอ)
- `prefers-reduced-motion` ยังอ่านรู้เรื่องครบทุกฉาก (แอนิเมชันเหลือแค่เฟด)

## 8. สิ่งที่ Claude สำรวจแล้ว (ข้อเท็จจริงของโมเดลที่ใช้เล่า)

- แอปหลัก: React 19 + TypeScript + Vite 6 · กราฟ Recharts · deploy GitHub Pages ด้วยข้อมูลตัวอย่างเท่านั้น
- ข้อมูลสองทาง: **ข้อมูลใหม่** ฟอร์ม → Apps Script → Google Sheet · **ข้อมูลเก่า** Excel → ETL (Python) → JSON → เบราว์เซอร์
- ข้อมูลจริง: ไฟล์รายได้ 29 ไฟล์ เกือบ 2 ล้านแถว · ทะเบียนกองรถ 899 คัน · ไฟล์ต้นทุนรายเที่ยว ใบละได้ถึง 3 ทะเบียน
- เมนูหลัก: **Executive Dashboard** (4 ส่วน: Profit Per Route · Inefficient Transportation Cost · Vehicle Utilization Cost ·
  Customer Performance + Performance Index /100) · **Overall Dashboard** (Vehicle Utilization · Damage Rate · Empty Trips ·
  Inefficient Transportation Cost · Contribution Margin · Vehicle Utilization Cost) · Manager Dashboard · ระบบงาน บิล → จัดรถ → คนขับ → บัญชี · Cost to Serve
- ตัวเลขชุดตัวอย่าง (ถูกสุ่มค่า **ห้ามใช้เป็นข้อสรุป**): 4,407 เที่ยว · 177 เส้นทาง · 400 เที่ยววิ่งเปล่า · Load Factor เฉลี่ย 58.9% ·
  ต้นทุนที่จมกับที่ว่าง 42.9% · PI รวม 56/100 · Margin 57% (สูงเกินจริงเพราะข้อมูลถูกสุ่ม)
